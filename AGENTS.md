# AGENTS.md

## Repository context

This repository is a CS100 HW8 I, Zombie C++ project.

The goal is to produce a stable, playable I, Zombie game using the provided framework. The student code should mainly live under `src/`, `include/`, and student-created `CMakeLists.txt` files.

Do not review `third_party/`, generated build directories, or provided framework files unless the pull request directly modifies them. In particular, be very suspicious of unnecessary changes under `src/Framework`.

## Build and hard checks

The repository has a GitHub Actions workflow named `Build and Quality Checks`.

Before giving final review conclusions, try to inspect the PR comment titled:

`CS100 HW8 Hard Checks Report`

It is generated by `.github/workflows/build.yml` and contains the results of these hard checks:

* H00: CMake configure and build must succeed.
* H01: No compiler warnings from student code.
* H02: No manual memory management.
* H03: Required `.cpp` / `.hpp` files and CMake structure.
* H04: Use `utils.hpp` enum values, not raw IDs.
* H05: No concrete type checks.
* H06: No C-style casts.

If the hard-check report is visible and a check failed, mention it near the top of the review and connect it to the corresponding HW8 rule.

If the report is not visible, continue reviewing the PR diff normally and do not assume the checks passed.

## Review guidelines

Use Chinese for review comments.

Act like a strict but helpful CS100 TA. Focus on serious issues that may cause grading deduction, undefined behavior, crashes, or failed offline check. Do not nitpick formatting unless it affects correctness, maintainability, or the HW8 code-quality rubric.

At the top of the review, include:

* Overall risk: Low / Medium / High
* Must fix before submission
* Should fix if time
* Looks good

For each finding, use this format:

### [Severity] [Rule ID] Short title

* Location:
* Problem:
* Why it may lose points:
* Suggested fix:
* Confidence:

Severity levels:

* `BLOCKING`: likely build failure, runtime crash, or direct major deduction
* `MAJOR`: likely code-quality deduction or serious design issue
* `MINOR`: possible deduction or improvement
* `INFO`: note only

## CS100 HW8 code-quality rules to enforce

### R01. No warnings from student's code

Flag likely compiler warnings in student code, including:

* unused variables
* unused parameters
* missing return in non-void functions
* signed/unsigned comparison issues
* uninitialized fields
* implicit narrowing conversions
* shadowing that may cause bugs
* non-virtual destructor in a polymorphic base class
* overloaded virtual functions being hidden accidentally

Warnings from `third_party/` or provided framework files should not count.

### R02. No manual memory management

Flag:

* owning raw `new`
* `delete`
* `malloc`, `calloc`, `realloc`, `free`
* containers of owning raw pointers
* manual deletion of game objects
* returning raw owning pointers
* `std::shared_ptr<T>(this)`
* unsafe or unnecessary `shared_from_this()`

Expected style:

* use `std::shared_ptr`, `std::unique_ptr`, `std::make_shared`, `std::make_unique`
* use standard containers
* game objects should mark themselves dead
* `GameWorld` should own and erase game objects
* call `shared_from_this()` only when the object is already managed by a `shared_ptr` and only when necessary

### R03. Multi-file structure and CMake organization

Flag:

* all code crammed into one file
* missing new `.cpp` / `.hpp` files
* large method bodies placed in headers without good reason
* new `.cpp` file not added to CMake
* student-created subdirectory without `CMakeLists.txt`
* missing `add_subdirectory(...)`
* missing `target_link_libraries(...)` for student libraries
* fragile include paths

Expected style:

* declarations in `.hpp`
* definitions in `.cpp`
* student source subdirectories have `CMakeLists.txt`
* new code is actually linked into the build

### R04. Avoid copied code for similar classes

Flag duplicated logic in:

* zombie `Update()`
* plant damage/death handling
* card `OnClick()`
* projectile movement/collision
* cooldown logic
* HP/state handling
* coordinate conversion

Expected style:

* common zombie behavior in a `Zombie` base class
* common plant behavior in a `Plant` base class
* common shooter behavior in a `Shooter` base class if Peashooter and Repeater both exist
* common card behavior in a `ZombieCard` base class or generic card design
* helper functions for repeated collision/coordinate logic

### R05. Use `enum class`; avoid magic numbers and magic strings

Flag:

* plain `enum` when `enum class` would work
* magic numbers for object type, state, direction, row/col meaning, cooldown state, etc.
* magic strings for state/type identifiers
* hard-coded image/animation/layer IDs as integers
* repeated raw constants for prices, HP, damage, speed, cooldown, grid sizes, or stage counts

Allowed:

* obvious natural values like `0`, `1`, `-1`
* coordinates or dimensions when clearly tied to framework constants
* named `constexpr` constants with meaningful names

Expected style:

* use `enum class` for states/categories
* use named constants such as `kRegularZombieCost`, `kPeaDamage`, `kPeashooterCooldown`
* use framework constants and enums from `utils.hpp`

### R06. Correctly use enums and constants from `utils.hpp`

Flag:

* `ChangeImage(3)` instead of `ChangeImage(ImageID::...)`
* `PlayAnimation(1)` instead of `PlayAnimation(AnimID::...)`
* `LayerID(2)` or `static_cast<LayerID>(2)` without strong justification
* raw numeric image/animation/layer IDs
* comparing integer image IDs
* duplicating framework constants instead of using `WINDOW_WIDTH`, `WINDOW_HEIGHT`, `ImageID::...`, `AnimID::...`, `LayerID::...`

Expected style:

* use `ImageID::...`
* use `AnimID::...`
* use `LayerID::...`
* define new image/animation IDs meaningfully if custom assets are added

### R07. Data members should be private by default

Flag:

* public data members in normal classes
* excessive protected data members
* exposed internal containers
* returning non-const references to internal game object lists
* exposing `GameWorld` object containers or iterators to `GameObject`

Expected style:

* most data members are `private`
* use `protected` only when subclass access is truly needed
* use public behavior methods instead of exposing raw storage
* `GameWorld` should manage its own containers

Acceptable exception:

* a very simple aggregate-like struct may have public fields if that intent is obvious

### R08. Do not identify concrete object types directly

Flag:

* `dynamic_cast` used to detect `Peashooter`, `Sunflower`, `RegularZombie`, etc.
* `typeid`
* comparing `ImageID` to determine object type
* using animation ID or image ID as object type
* many functions like `IsPeashooter()`, `IsSunflower()`, `IsRegularZombie()`

Allowed:

* broad category methods like `IsZombie()`, `IsPlant()`, `IsProjectile()`
* behavior predicates like `CanBeHitByPea()`, `CanBeEatenByZombie()`, `CanJumpOver()`
* a scoped `enum class ObjectCategory` or `enum class CollisionGroup`
* virtual behavior such as `TakeDamage`, `OnCollideWithZombie`, `CanBeEaten`, etc.

Expected style:

* collision and behavior should use virtual functions, broad categories, or polymorphism
* do not depend on concrete implementation classes unless there is a strong reason

### R09. Correct use of `static`, `const`, and `virtual`

Flag:

* member functions that do not use `this` and should probably be `static`
* getter/query methods that should be `const`
* missing `override` on overridden virtual functions
* unnecessary `virtual` on every method
* base class without virtual destructor when used polymorphically
* non-const methods used only to read state

Expected style:

* use `const` for read-only methods
* use `override` on all overrides
* use virtual only when runtime polymorphism is needed
* use `static` for helpers independent of object state

### R10. Reasonable inheritance design

Flag suspicious inheritance such as:

* `Repeater : public Peashooter`
* `BucketheadZombie : public RegularZombie` if it causes awkward HP/image hacks
* `ConeheadZombie : public RegularZombie` if common behavior should be in `Zombie`
* unrelated objects inheriting only to reuse code
* base classes with fields irrelevant to many subclasses
* multiple inheritance without a clear reason

Expected style:

* all game objects derive from `GameObject`
* moving/eating zombies share a `Zombie` base
* damageable plants share a `Plant` base
* shooters may share a `Shooter` base
* projectile-like objects may share a `Projectile` base
* cards may share a `ZombieCard` base or generic card design
* prefer composition/helper functions when inheritance is not semantically correct

### R11. Prefer constructor initializer lists

Flag:

* constructor body assigning members that could be initialized in initializer list
* base class constructor calls not clearly in initializer lists
* default-construct-then-assign pattern
* uninitialized members

Expected style:

* initialize base classes and members in constructor initializer lists
* member initialization order should match declaration order
* especially important for classes derived from framework object bases

### R12. Avoid unnecessary explicit casts; never use C-style casts

Flag:

* C-style casts like `(int)x`, `(double)y`, `(SomeType*)ptr`
* unnecessary `static_cast`
* casts hiding bad design
* enum/int casts without clear reason
* `reinterpret_cast` unless extremely justified

Allowed:

* construction expressions like `Type(args...)` or `Type{args...}`
* minimal justified `static_cast` for safe numeric conversion
* casts required by framework interfaces, if unavoidable and documented

### R13. Declare variables close to first use; avoid global variables

Flag:

* non-const global variables
* global containers
* global mutable game state
* file-scope mutable variables
* local variables declared far before use
* loop variables declared outside loops without reason

Allowed:

* `constexpr` constants
* `const` named configuration constants
* small helper functions in anonymous namespace

Expected style:

* game state belongs in `GameWorld`
* object state belongs in the corresponding class
* local variables should be declared near first use

## HW8 functional risks to mention if seen

Also flag these when visible in the diff:

* modifying `src/Framework` unnecessarily
* not cleaning up dead objects safely
* erasing from `std::list` incorrectly during range-for iteration
* object deletes itself instead of marking itself dead
* same plant/zombie/pea can be deleted twice
* plant grid occupancy not cleared when a plant dies
* zombie remains in eating state after plant is gone
* sun can become negative
* card cooldown starts when selecting card instead of after successful deployment
* clicking deployment area without selected card still creates zombie
* deployment succeeds with insufficient sun
* overlapping zombies can spawn at the same position
* text display not updated after sun/stage/brain changes
* `GameWorld::Init`, `GameWorld::Update`, or `GameWorld::CleanUp` called manually by student code
* `CleanUp()` does not clear all containers and owned text/object pointers
* code only works with an absolute local asset path

## Review behavior

Be strict about HW8 grading risks, but do not invent problems.

Do not provide a full replacement implementation.

Do not suggest over-engineering. The target is a simple, stable, maintainable CS100 homework game, not a professional game engine.

When the code is acceptable, say so clearly.
